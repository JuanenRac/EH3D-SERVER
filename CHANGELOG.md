# Changelog

All notable changes to this project are documented here.

## [Unreleased]

- **Third-party notices in every package (`docs/THIRD_PARTY_NOTICES`):** the packages of the releases now carry the copyright notices and licence texts of the Rust crates and of the data the program is built with, and the CI fails when a new dependency or licence is not in the file.

- **A job that goes on after a stop asks apart before the tool goes down into the work (safety, changes what a client has to answer):** with the head over the point and the spindle the program had on already turning, every G-code machine not said to carry a laser waits once more before the `G1 Z` of the resume sequence, with its own question (`pause.plunge`; without the name it is refused, whatever `answer_needs_question` says). It looks at the controller once more after the answer, and cancelling there stops the machine without going down. The `Pause` of the API document also lists `power_on` and `plunge`. Tried on the simulator only, not on a machine.
- The test counts of the eight READMEs include the new test of the number format of the drill layers.

- **A drill file that does not declare its number format is refused until the request names one (safety, changes what is accepted):** drilling plans from files and the `drill` job of the CAM service no longer read a machine file without a header or an `INCH` header alone by supposing it. Send `drill_format` (`params.drill_format` for the CAM service): `mils` gives the old reading of the plans; `inch-2.4-tz`, `inch-2.4-lz`, `metric-3.3-tz`, `metric-3.3-lz`. The clients do not offer the choice yet.
- **The drill reader of the layers follows what the file declares:** `TZ` and `LZ` were applied the wrong way round (a file with `INCH,TZ` and numbers without a point was placed a hundred times off), and `FILE_FORMAT` and a number mask were not looked at.


- **The Chinese help of `grbl_spindle_stop_on_pause` is worded with characters the screens of the suite can draw.**
- **A pause can stop the spindle, off by default (not tried on a machine):** with `grbl_spindle_stop_on_pause` the pause of a job on a GRBL machine also sends the safety door byte (`0x84`), which stops the spindle and the coolant until the job goes on. The setting is in `server.cfg` and in the settings contract with its help in eight languages. A pause whose door state is not confirmed stops the job. The server takes EH3D-COMMON v0.3.9.
- **A pause given while a line waits for its `ok` can be resumed:** the job counts as held and the resume is written to the port at once; before, a controller that does not answer lines while held left the job shown as running, with nothing but a cancel to end the wait (seen by reading the code, not on a machine).

- **A job that goes on after a stop asks apart before the spindle or the laser goes on (safety):** the `M3` or `M4` of the resume sequence is sent only after a second confirmation that names its own question (`pause.power_on`; without the name it is refused, whatever `answer_needs_question` says). The new machine member `tool_head` (`laser`, `spindle` or empty) says what the machine carries: on a laser the head is back over the point before the beam goes on; a machine said to carry a spindle, or that names its spindle (`original`, `vfd`) and says nothing, asks once as before; a machine that says neither asks twice. 3 new tests. Simulator only.

- **A job file that would be planned only in part is refused (safety):** a drilling file with slots or routed moves was planned from its holes alone, and a plot with a number that cannot be read or a coordinate with no pair was planned with its points moved. The job is now refused, with `bad_ncd` and the line, or `bad_path` and what the shared plot reader tells. A job that was accepted before may be refused now. 1 test. Checked with the planner only; not tried on a machine.
- **An answer names the question it answers (safety):** while a job waits, `pause.question` identifies what it asks, with a new identifier every time. `POST /jobs/:id/confirm` and `/resume` take `{"question": ...}` and answer `409 question_changed` when the job asks something else by then, so a screen or a person cannot answer a question they have not seen (the start of the spindle that follows a tool change). Each question is answered once, also by clients that send no identifier. New setting `answer_needs_question` (off, so that published clients keep working; on: an answer without the identifier is `409 question_required`; 106 settings now). The resume of the work queue and of the compatibility routes only lets go a job an operator held. Checked against the simulator; not tried on a machine.

## [0.2.7] - Limits that a spaced number could skip, real-time characters refused and a prudent stop and resume (not tried on a machine)

- **Blanks no longer hide a speed or a feed from the limits (safety):** the lines of a program are read with the G-code reader of the suite at a later commit, which reads them as GRBL does (`S1 000` is `S1000`, `F1 000` is `F1000`). Before, the findings `rpm_over_limit` and `feed_over_limit` and the limits of the spindle could be passed that way. The cut of the `S` words (spindle switch on `warn`) takes the number the same way, the unit a line sets counts for all its words, the feed of a jog is judged, and the CAM verification judges feeds in inches and moves that do not name their motion.
- **A command of the controller is refused wherever it stands in a line (safety):** `$`, `!`, `~`, `?`, control characters and characters outside ASCII, not only at the start; blanks no longer hide `$RST` on a machine that allows `$` lines.
- **A G-code program the controller would read in another way is refused, with the line and the reason (safety):** unreadable or repeated words, `G93`/`G95`, canned cycles, cutter compensation, a comment that is not closed, a carriage return inside a line, code after `M2`/`M30`, a block-delete line and a wait for the operator (`M0`, `M1`) with the spindle on. A program that ends with the spindle or the coolant on is given `M5`/`M9`. A job that was accepted before may be refused now.
- **3D printer programs are judged more closely (safety):** the `R` of `M109`/`M190` and the temperature of `M303`, a feed set on a line of its own or of an arc, the end of arcs against the bed; a line that moves or heats and cannot be read for certain, and `M23`/`M28`/`M29`/`M32`, are refused. A line of G-code sent to Moonraker is written whole into the address, so it cannot carry a second command.
- **Laser programs are not read in part (safety):** code after `M2`/`M30`, repeated words, an unclosed comment and a carriage return inside a line are refused, where lines were left out in silence. A CNC job with an arc outside the XY plane is refused.

- **A G-code job that is stopped waits for the machine to stand still before the reset (safety):** the feed hold goes at once, the state is read from the controller until it says the machine stands still (`Hold:0`, idle or an open door that stands), and only then the soft reset, which stops the spindle, goes out. When the controller does not say so within `grbl_stop_wait_s` (3 s), goes into alarm or the link fails, the reset goes all the same and the job says that the position of the machine is not known; a homing cycle is reset at once. The same applies to a stop after an error. Checked against stand-ins of the controller; not tried on a machine.
- **Going on from a stopped G-code job takes the tool back safely (safety):** after a person confirms, the tool goes up to `resume_safe_z_mm`, the spindle the program had on is started and given `resume_spindle_wait_s`, the head crosses to the point the program had reached, goes down at no more than `resume_plunge_feed_mm_min` and the program goes on. Before, no line moved the tool back and, with `restore_outputs`, the spindle started before the confirmation. The spindle is now started also when `restore_outputs` is off, which only decides the coolant.
- **A job that goes on is refused, with the reason, where the state or the position is not certain (safety):** the controller has to be idle, both before and after the confirmation, and, for a job the server goes on by itself, the machine has to be where the stopped job left it (`resume_position_tolerance_um`). The server does not go on by itself from a job whose stop was not confirmed or that was running when the server ended; a person then puts the machine right and names the line. A line after which the place of the tool cannot be read from the program (relative distances, `G92`, `G43.1`, a canned cycle, `G28`, `G30`, `G53`, a probe, a change of offsets) is refused even when it is named. On a controller that restarts when its port is opened the position is lost and the check refuses to go on by itself.
- Fix the state of a resumed job: after the confirmation it stayed `waiting_operator` while it ran, so it could not be paused and took a second confirmation.
- Five settings for it, in the contract of the settings and in `server.cfg.example`: `grbl_stop_wait_s`, `resume_safe_z_mm`, `resume_spindle_wait_s`, `resume_plunge_feed_mm_min` and `resume_position_tolerance_um` (105 settings now).

## [0.2.6] - Safer resume and stop of machine jobs, updated TLS library (not tried on a machine)

- **TLS library updated (security):** rustls is at 0.23.46 (it was 0.23.28), for the advisories published against the earlier version.
- **The server is built with the current drilling and routing engines (safety):** EH3D-DRILLPRO at v0.2.4 (it was v0.1.7), EH3D-ROUTEPRO with its latest tool changer fix (it was v0.1.6) and the shared repository EH3D-COMMON at v0.3.6 (it was v0.2.1), so the jobs the server runs have the waits, the stops and the tool changes of those programs. Checked by the tests against the simulator; not tried on a machine.
- **Going on from a stopped G-code job is more careful (safety):** the motion in force (`G0` to `G3`) is given back with the other codes, the margin `resume_margin_lines` counts lines that move, and where the server cannot tell where to go on from (relative distances, offsets the controller loses, a job that ran on the tool changer) it says why and a person names the line.
- **Stopping a G-code job (safety):** a controller that cannot be read during the last moves is now told to stop, and no line can follow the real-time stop on the port.
- **Releases have a signed record, and the update helper asks for it (security):** `eh3d-release.json` says the repository, the version and the name, architecture, size and SHA-256 of every file of a release, and is signed like the files. Every version of EH3D-SERVER after 0.2.5 and of EH3D-STUDIO after 0.2.0 is installed only with it, and a record that any release publishes must agree with the download. Earlier releases, which only have the `.sig` of each file, are installed as before (`docs/DEPLOY.md`, "The record of a release").
- **A token that expires opens no account (security):** it does not make users, set passwords, enable users or raise roles (`403 forbidden_scope`), whatever its role and scopes; a login of a person and a token without expiry do as before. A program that provisions users needs a token without expiry (`docs/API.md`).

## [0.2.5] - Stricter token permissions, owners by identifier, version checked on updates and faster node polling

- **The nodes of the pick-and-place machines stay heard (safety):** `pnp_node_poll_s` is 1 by default (it was 5, and a head goes to its safe state after 2 seconds without being asked); each node is asked on its own connection without waiting for the answers still due, of it or of another node; and an interval that is too slow for a node is said on the console and in `GET /api/v1/pnp/nodes` (`warnings`, and `poll_too_slow` of each node). A `server.cfg` that names a slower interval keeps it and gets the warning.
- **The update helper asks a package which version it is (security):** besides the hash and the signature, the version the package declares inside (the `version.json` of the pages, or the name of the folder of the server) must be the one the release announces. The published releases already do; a component of your own in `--config` must too.
- **A new user with the name of a deleted one is another person:** every user has an identifier that is never given again, and projects, shares, artifacts, uploads, tasks, jobs, locks and notifications are filed under it (the API still shows the name). Users that exist keep everything, with nothing to move. What a deleted user made is left to the administrators.
- **A token with scopes gives no more than it has (security):** it does not make, change or delete administrators; it makes another user, sets a password, enables one or raises a role only when it carries the scopes of that role; and it makes the key of a 3D printer only with the scopes of what the key does. A program that provisions users with an `admin:users` token must be given those scopes too (`docs/API.md`), or answers `403 forbidden_scope`.
- **A token made by a token that expires ends no later than it (security);** such a token rotates only tokens that end no later, and makes no key of a 3D printer.
- Fix the rotation of a token (security): a token limited to some scopes, with `admin:tokens`, could rotate any token, an administrator's without limits among them, and read its new secret. It may now rotate only a token limited to some of the same scopes (`403 forbidden_scope`).
- Fix the change of the own password (security): wrong old passwords were not counted, so somebody holding an open session could guess the password without end. They now count like wrong passwords of a login (`429 throttled`).
- Fix the optional body of `POST /jobs/:id/resume-from` and of the quality check of the head (safety): a body that did not read was ignored whole, so a job could be made without the tools that had to be left out. It is now refused (`400 bad_request`).
- Fix the reading of bodies: a list where an object is expected was taken by the position of its items. It is now refused (`422 bad_request`).
- Fix the writing of the files of the server on Windows: the old file was removed before the new one took its place, so a power cut or a refused rename in between left no file, which read as a server with nothing yet (no users among it). The new file now replaces the old one in one step.
- Fix a record of the artifact store whose hash is not a hash (a damaged file): checking the store stopped with a panic; it now says the file is missing.

## [0.2.4] - Live status of printers, read only, with a Bambu LAN and a Moonraker adapter and a simulator

- **The 3D printers the server watches, read only:** `GET /api/v1/printers` and `GET /api/v1/printers/:id` give, for several printers at once, one contract (`eh3d.printers.status/1`): state, temperatures with their targets, progress, time left, layers, alerts (the health codes of a Bambu printer, a failed print, a stopped firmware), whether there is a camera, capabilities and health. One adapter for each family of protocol: Bambu Lab in LAN mode (MQTT over TLS with the certificate pinned, only while `bambu_lan_enabled` is on; the only message published asks for the whole state) and Klipper through Moonraker (two `GET` requests). Each can be simulated. There is no route and no code path that sends a printer an order, a temperature, G-code or a file. `POST`, `PUT` and `DELETE` (administrator) change the list of the server only. What a printer did not say, or a number that cannot be right, is `null`, never zero. Tried against printers in memory only.
- **Five settings for the printers, in the contract of the settings:** `printers_enabled` (off by default: the routes answer `501 printers_off` and no connection to a printer is opened), `printers_max`, `printer_poll_s`, `printer_stale_s` and `printer_timeout_s` (100 settings now). The access code or key of a printer is kept apart in `printer-secrets.json`, shown as `***`, and never logged or audited; a body that does not read is refused without quoting it. `eh3d-server --check` also verifies the two files. New error codes: `printers_off`, `unknown_printer`, `bad_printer`, `printer_exists` and `printers_full`. The websocket sends `{"type":"printer",...}` when the health, the state or the alerts of a printer change.
- Fix the answer of a printer or a node sent in chunks: a chunk that said it was bigger than any number could stop the request with a panic.
- Fix the time limit of a request to a printer over HTTP: a printer that gave its answer a byte at a time held the request for ever; the whole answer now has a limit.
- Fix the reading of a Bambu Lab printer: one that never stopped talking kept the question from ending.

## [0.2.3] - Header injection and temperature reading fixes of the head node and the Marlin simulator, safer G-code files, and many more tests

- Fix the request to the node of the drill head (security): a line break or another control character in the address, the path or the token of the node could begin another header of the request; they are now refused or dropped.
- Fix the reading of the temperatures of a printer (safety): a reading that is not a finite number (`nan`, `inf`) is no longer taken as a temperature, because every comparison with it is false and a limit would never trip.
- Fix the printer in memory of the Marlin protocol: a time step that is not a number, or far too long, no longer poisons the heaters or overflows the count of lines done, and asking for a line again after the last possible number no longer overflows.
- Fix the file of settings: a file saved with a byte order mark, as some editors of Windows do, was refused on its first line (unknown key or missing equal sign); the mark is now ignored.
- Fix the writer of binary G-code: a limit of a block that fell inside a letter of more than one byte (a comment with an accent) stopped the server with a panic; the block now ends before the letter.
- Fix the order of a shared catalog by a field that holds numbers and text: a number compared as text with another text made the order a cycle, so the result depended on the order the items came in and a sort of a long list could stop with a panic. Numbers now come before text.
- Add tests that hunt for bugs in the pure parts of the server: the lines of the Marlin protocol and the printer in memory, the file of settings and every range of it, the switches of the security page, the feed of events, the upload, search and order of the shared catalogs, the ranges of an upload, the names of applications and users, the versions, the announcement on the network, the audit, the limits of a spindle, binary G-code and the readers of STL and 3MF files.
- Add tests of the pure parts of the server: the ids and their order, the two compressions (round trip, checksums, damaged and cut streams), the multipart reader, the simulated clock, the G-code comment and speed helpers and the catalog of errors.

## [0.2.2] - A register of the feeder and head nodes of the pick-and-place machines and the authorization of a job by the hash of its toolpath

- **A registry of the feeder and head nodes of the pick-and-place machines:** `GET`/`POST /api/v1/pnp/nodes`, `GET`/`PUT`/`DELETE /api/v1/pnp/nodes/:id` and `POST /api/v1/pnp/nodes/:id/poll` keep a list of the nodes (kind `feeder` or `head`, address, token, and the `pnp` machine each belongs to), ask them for `GET /api/status` and then for a read that needs their token (so a node that goes safe when it does not hear the server keeps hearing it), and show what each said last: the feeders and their low, empty and faulted counts, or the nozzles and their faults. The token is never shown, logged or audited (`********`); a node is registered by an administrator, asked by an operator, read by a viewer, and every change is audited. Simulator only: each node says `evidence: simulator`.
- **A node that cannot be relied on is not ready, and holds its machine:** the server degrades towards what is safer. Only a node whose own check says `ok` or `warn` is ready; a node never asked, switched off, unreachable, answering something that is not its contract, refusing the token, saying it is safe, failing its own check, or quiet for `pnp_node_silence_s` (never less than two polls) is not. A job of a `pnp` machine that has such a node switched on is refused at start with `409 pnp_node_not_ready` and the reason; a machine with no node behaves as before. The detail of the machine lists its nodes, the fleet gets a `pnp_nodes` count while the switch is on, and the websocket sends `{"type":"pnp_node",...}` when a node changes its health.
- **Five settings for the nodes, in the contract of the settings:** `pnp_nodes_enabled` (off by default: the routes answer `501 pnp_nodes_off` and no connection to a node is opened), `pnp_nodes_max`, `pnp_node_poll_s`, `pnp_node_silence_s` and `pnp_node_timeout_s`, in `server.cfg.example`, with their ranges in the code and their label and help in the eight languages in `docs/settings-contract.json` (95 settings now with the one below); `eh3d-server --check` also verifies that the list of nodes on disk reads.
- **A job of the queue has a hash and can be authorised by it:** every job of `/api/v1/work/jobs` carries a `toolpath_sha256` (the plugin, the machine and the request as resolved, with the keys in order) made when it is prepared; `POST /api/v1/work/jobs/:id/authorize` (operator, the scope `jobs:authorize` that no request used until now, audited) records who authorised which hash, and `409 stale_authorization` refuses another one. A start may name the hash it expects and is refused with the same code when the job is not the one that was shown; a body that does not read is `400 bad_request`, never ignored.
- **A switch to start a job only after its authorization:** `work_require_authorization` (off by default, the stricter choice when on, in the contract of the settings) makes a job of `laser`, `pnp` or `cnc` start only when a person authorised its present hash: `409 authorization_required` otherwise. Nothing changes while it is off.
- **New error codes in the catalog, the API document and `docs/error-codes.json`:** `pnp_nodes_off`, `unknown_pnp_node`, `bad_pnp_node`, `pnp_node_exists`, `pnp_nodes_full`, `pnp_node_disabled`, `pnp_node_not_ready`, `stale_authorization` and `authorization_required`; the new routes are in the OpenAPI document and in `docs/ROUTES.md`.
- **Tests with fixed seeds against nodes in memory:** `tests/pnp_nodes.rs` runs a feeder and a head as small servers on `127.0.0.1` with a port the system gives (no real network), through the real router: roles and scopes, the token never shown, a refused token, an answer that is not the contract, a quiet node, the hold of a machine, the events, the poller on a timer and a seeded life of 120 steps where the health always follows the node; the module has 12 more tests (summaries, the order of the safe rules, a seeded thousand made-up answers). `tests/job_auth.rs` covers the hash (it does not depend on the order of the keys), the authorization with its scope, the switch and 200 seeded made-up hashes that are never taken for the real one.

## [0.2.1] - A light read-only view of the settings for any login with a hash of the contract, a quiet check of every route and the safety of the machines of the plugins

- **A light, read-only view of the settings for the screens of the machines:** `GET /api/v1/settings/values` answers, for any login or token (a viewer, an operator or an administrator, no scope), the value in force of each key of `server.cfg`, where it comes from (`origin`: `file`, or `override` when a change through the security page differs from the file) and whether `PUT /api/v1/auth/policy` changes it (`editable`). It has no texts, no secret and no path of the computer: a key the contract marks as `secret` shows `***` and `secret: true`, a key that is a path is `hidden`, and a long text or list is cut (`truncated`). It is about 6 KB and never more than 16 KiB, against 250 KB of the full contract, which still needs an administrator with `admin:policy`. `?keys=a,b` and `?group=id` narrow it; a key, a group or a query that does not fit is `422 bad_request` and the detail names it.
- **The light view has an `ETag` and the contract has a hash:** every answer of the view carries an `ETag` (the SHA-256 of its text) and `Cache-Control: private, no-cache`, and `If-None-Match` with the tag, a list of tags or `*` is answered `304` with no body, so a screen that asks every few seconds reads the body only when something changed. `contract_hash` (the SHA-256 of `docs/settings-contract.json` with LF line ends, the same on every machine) is in the view and in `GET /api/v1/settings/contract`, so a client that keeps a copy of the contract knows whether it is still the server's.
- **The contract describes the light view:** `docs/settings-contract.json` has a new `read_light` section (route, role, schema, how the answer is read, the cache, the query, the errors, the mark of a secret and the limits); no key, entry or order of the contract changed, so the copies of the clients pass their parity guard as they are. The generator, `docs/openapi.*` (`SettingsValues`, with the `304`), `docs/ROUTES.md`, `docs/API.md`, `docs/AUTH.md`, `docs/SERVICES.md` and `docs/CLIENT_SYNC.md` say the same, and no error code was added.
- **`eh3d-server --check` verifies the light view:** it builds the view for the settings and the changes of the security page it would start from and fails (exit code 2) if it were bigger than its limit.
- **Tests of the light view:** the module `settings` has 8 more tests (the limits of the contract are the constants of the code, a hash that does not depend on the line ends, a secret key shows the mark and its value is nowhere in the view for each kind of key, a path has no value, the size with the biggest values the settings can have, the origin and the tag, the selection, and a fuzz of the query from a fixed seed) and `tests/settings_values.rs` has 9 end to end (every role and the screen of a machine read it and nobody who is not logged in, the shape of every key, the size against the full contract, the tag and the `304`, the hash of the file, the query, a fuzz through the router, the refusals in the audit, and the policy unchanged).
- **The tests of the programs build their client through the program's own constructor:** `tests/programs.rs` wrote the fields of the client of DRILLPRO one by one, which stopped compiling when that client gained fields for the limits of its link; it now makes the client with `Client::new` from a default connection, so the server builds against the released programs and against the ones in development.
- **`eh3d-server --check [--config FILE]` verifies without starting:** it reads the file of the settings, the changes of the security page (`policy.json`) and the contract of the settings, writes nothing, prints one line per check (`ok:` or `FAILED:`) and exits 0 when all pass and 2 when one does not (a check that cannot be made counts as not passed). Exit 1 stays for a server that could not start and 2 for a command line that makes no sense. Covered by 3 tests in `src/check.rs` and `tests/cli_check.rs`.
- **The rule "degrade towards what is safer", written down and tested:** `docs/SAFE_DEGRADATION.md` says what the server does on each error path and what it never does; `tests/safe_degradation.rs` has 6 tests that fail when a path loosens a restriction or reports success (a plugin that fails latches the machine, a value of an interlock that is not understood is refused and the interlock holds, a refused write of the policy changes nothing, a closed or unknown login cannot release or change anything, a missing or wrong policy file never reads as loose and an unreadable one stops the start).
- **A feasibility pass over every simulated machine configuration:** `tests/machine_feasibility.rs` makes a machine of each plugin (`laser`, `pnp`, `cnc`, `pcb`, `printer3d`, `cam`, `gerber`, `vision`, `cad`, `demo`, and one of `bungard`) and checks that each is listed, is at rest, declares limits that are whole numbers above zero and settings with a help text, refuses a setting it does not have, and says in its detail `evidence: simulator` and `simulator_only`; it fails when a plugin that makes machines is not in the table.
- **Fuzz tests from a fixed seed of the readers of input:** `tests/fuzz_inputs.rs` feeds damaged and made-up data to the reader of binary G-code (four compressions), the deflate and heatshrink readers and the 3MF reader, and random JSON bodies to the routes of slicing, jobs, farm, machines and policy; nothing may panic and no route may answer with a 5xx.
- **Two tests no longer share a data folder:** two tests of the plugin tests built their server with the same name, so they kept their data in the same folder and the one that started later emptied it under the other, which then failed with `500 storage` on a random run; one is renamed, and `tests/unique_server_dirs.rs` fails when a test file builds two servers with the same name.

## [0.2.0] - Bambu LAN link over a pinned TLS certificate, bgcode files, kept logins and a contract of every setting

- **A contract of every setting of the server, for Studio and the apps:** `GET /api/v1/settings/contract` (administrator, scope `admin:policy`) gives, for each of the 89 keys of `server.cfg`, its group, type (boolean, integer, string or list), range, default and unit, whether a change is in force at once or read when the server starts, the route that writes it, the role and scope it needs, whether it is a secret, the kind of risk, and a label, a short help and a warning in en, es, de, fr, it, ja, zh and pt. The answer also has `values` (the value in force of each key that is not a secret) and `server_version`, so a client can draw its whole settings page from it and turn any switch on or off.
- **`docs/settings-contract.json` and the generator that checks it:** the document `eh3d.settings.contract/1` is written by `tools/gen_settings_contract.py` from the code (the keys `config::parse` accepts with their ranges, the defaults of `ServerConfig::default()` and the lists of `src/policy.rs`) and from the texts of `tools/settings_contract_texts.py`; the server embeds the file. `--check`, which the CI runs, fails when a key of the code has no entry, when an entry names a key the code does not have, when a language is missing, when `server.cfg.example` and the code disagree on the keys or on a default, and when the file on disk is not what the sources give.
- **`PUT /api/v1/auth/policy` says whether the change needs a restart:** the answer has `changed` with the key, the old and the new value, `apply` (`now` or `restart`) and `restart_required`; a key that is read when the server starts (`network_open`) is kept at once and says `restart`.

- **The audit of a policy change hides the value of a secret key:** the old and the new value of a change are written as `***` for a key that the contract marks `secret` (no key of `server.cfg` is one today), and such a key never has a value in the answer of the contract.

- **The requests of administration have their own scopes:** the users, the tokens (and the keys), the security switches (and the audit) and the updates now need `admin:users`, `admin:tokens`, `admin:policy` and `admin:updates` from a token that has scopes, so an administrator's token of a design program (for instance one with `catalog:write`) can no longer make users or tokens; a token without scopes still does whatever its role allows, and a person is not affected. A program that really has to administer needs a new token with the scope it uses (see the API document); the new scopes are listed in the document of the interface and in the table of routes. Tests go over every route of administration with and without its scope.
- **What the server writes is private to its account:** the users, tokens, sessions, nodes and every other file written by the store are created with mode 0600 on Unix whatever umask the server was started with (before, only the systemd unit forced it); a test checks the file and its backup.
- **The login of an event stream is asked about by the clock:** the check every 30 seconds no longer restarts with each event, so a stream on a busy server is checked as often as a quiet one, and the identity is read again each time (a lowered role or a narrowed token applies without reconnecting).
- **A stop that arrives while a job is starting is no longer lost:** a job that is still connecting (its run not yet registered) records the stop and the start stops its run as soon as it exists, instead of answering that the job cannot be cancelled while the machine stop said it had stopped; test through the machine stop.
- **The update helper refuses to go back to an older version:** a signed release of an old version that is published again as the latest is no longer installed over a newer one; `--allow-downgrade` or `allow_downgrade` in the settings of the helper allows going back on purpose. Four more tests of the helper.
- **The update helper no longer writes through links in the shared folder:** the folder belongs to the account of the server and the helper runs as root, so a link left in the place of `status.json.tmp` (or of any other file the helper writes) made it write through the link. The temporary file is now created new (an existing link is removed, never followed), files are read without following links, and a request with an action other than check, apply, undo or clear_history is refused without copying its text into the history.
- **The first administrator is made from this computer by default once the network is open:** `local_until_setup` now applies by itself, while the server has no user, whenever `network_open` is on or `listen` names an address that is not this computer, so nobody else on the network can make the first administrator. - **A smoke test of the binary in the release workflow:** `tools/smoke_binary.py` starts the built server on a free port, checks its health check against `--version` and stops it.
- **A nightly backup of the data folder:** `deploy/eh3d-backup.py` with a systemd timer writes a `.tar.gz` (owner-only, read back to check it, files being written left out) and keeps the newest ones (`backup.cfg`: `source`, `dest`, `keep`); `docs/DEPLOY.md` explains the restore. 7 tests.
- **A guide to HTTPS that can be copied:** `deploy/Caddyfile.example` (Caddy with its own certificate authority, the server listening only on 127.0.0.1) and the steps to trust the certificate; it says to turn `login_ip_limit` off behind the proxy.
- **The tests of the helpers of the deployment run in the CI.**

- **Examples of the answers, made by the tests:** `tests/examples/*.json` (session, health, preview, error, job, jobs, fleet, spindle and updates) are made from the real router, and the tests fail when a file is not what the server answers; `tools/sync_api_examples.py` copies them to the clients, which read them in their own tests.
- **The last update can be undone:** `POST /api/v1/updates/undo` asks the helper to put back the version that the last update of a service left behind (the version installed takes its place, so doing it twice goes forward again); each component of `GET /api/v1/updates` says `can_undo` and, when the helper knows it, the `previous` version. The helper writes `previous.json`, marks what it installs with its version and restarts the server when it is the server that goes back; it refuses while a job is active. 6 tests.
- **The history of the updates can be emptied:** `POST /api/v1/updates/clear-history` asks the helper to empty `history.json`; that request is not kept in the history it empties.
- **A dry run of the exact plan before any job exists:** the steps of a drilling or routing job are followed on paper, the way the control unit reads them, and the view of the job gets `dry_run` (how far each axis goes from its switches, where the plan ends, the steps and the seconds, and whether it stays inside the course of the machine file). A plan that takes an axis past its course is refused with `422 outside_course`, saying which axis and by how much; the tuning of the machine decides with `dry_run = reject` (the default) or `warn` (the job goes through and the excess is listed), and `dry_run_margin_mm` (0.5) is the play that is forgiven.
- **Sanity checks of the work in the view:** `warnings` lists what looks wrong in the file (`tiny`: the whole work is smaller than `sanity_tiny_mm` in both directions, a wrong unit; `too_big`: bigger than the table; `far`: starts further than `sanity_far_mm` from the corner; `scale`: the machine file stretches the work; `out_of_course` with `warn`). They only warn; the thresholds are keys of the machine's tuning. 4 tests.

## [0.0.9] - The steps, the notes and the history of an update reach the Studio

- **The steps of an update with a percent:** the helper writes the steps of the job (download, check, install and restart of each service) with their state and the percent of the whole, and the server gives them in `GET /api/v1/updates` (`steps`, `percent`); the step that was running when a job failed is marked as failed.

## [0.0.8] - A stop that reaches the machine at once, files that survive a power cut and a token out of the address

- **Each dependency on a sibling repository by path says the version it needs** (`version = ">=0.0.1", path = "../EH3D-..."`), so Cargo stops at once when the sibling next to this one is older than the program expects.
- **Files that survive a power cut:** the JSON files of the server (users, tokens, machines, the list of the jobs and the request of each job) are flushed to the disk before they replace the old file and the folder is flushed after it; the file that is replaced (and the list of the jobs) is kept once as `<name>.bak`. A damaged file is still an error, but when the copy is good the error names it and says how to recover; it is never loaded by itself.
- **The slowest turn of the original spindle is 5000 rpm** (the figure of the maker's page; it started from 3000), and the documentation of the starting limits says 5000 to 63000 turns.
- **The stop button reaches the machine at once:** `POST /machines/:id/stop` ends the job that is active on a machine whoever asks and whatever the job is; on a GRBL machine the feed hold and the soft reset are written to the port from another thread (the port is shared, the waits are made in short turns), so a homing cycle or a long move no longer has to end before the stop is heard. A line that was waiting when the stop came does not make the job fail: it is cancelled. `POST /jobs/:id/cancel` takes the same way.
- **The token stays out of the address:** `POST /tickets` gives a ticket good for one use within 30 seconds, for the camera and the websocket; `?token=` in the address is refused unless `url_token = true` is set.
- **`local_until_setup` in `server.cfg`** (off by default: the server answers whoever reaches it, as it always did): while there is no user yet, only connections from 127.0.0.1 are answered (`403 local_only` for the rest), so nobody else on the network can make the first administrator; once there is a user it makes no difference.
- **The update helper can require a signature:** when the machine has a file of allowed signers (`/etc/eh3d-update.signers` or `--signers`), only a release that publishes `<file>.sig` (an OpenSSH signature made with `ssh-keygen -Y sign -n eh3d-release`) that verifies against one of those keys is installed; without the file it works as before and says in its log that the hash proves the file arrived whole, not who made it. No key is made by the project: the owner makes one and publishes the signatures.
- **The request of a job is a file of its own** (`requests/<id>.json`) and `jobs.json` no longer carries it; the files are written by a thread of their own, so the lock of the jobs is never held for the disk. A `jobs.json` of an older version is read and its requests are moved to files.

- The release workflow runs `cargo test --all-targets` before it builds the packages.

- **A resumed G-code job goes back a margin of lines** (`resume_margin_lines` in `server.cfg`, 16 by default, 0 to 1000): the controller takes lines ahead of the movement, so the last ones it took were not all done. The codes in force are still given back before the first move.
- **Wrong passwords are also counted by address** (`login_ip_limit`, 10 by default, 0 turns it off): the address is the one of the connection, never a header, and a person who tries many names from one address is slowed down without blocking the names of the others.

- **The secrets of the tuning text stay on the server:** `GET /machines` and `GET /machines/:id` show `head_token`, `node_token` and any other `*_token`, `*password` or `*_secret` key with an empty value, and a `PUT` that sends them empty keeps the stored ones.
- **A started job cannot be undone by a late start:** a job cancelled or removed while it was being planned is not started any more, and `DELETE /jobs/:id` checks and removes under one lock.
- **A machine with a job running is not edited:** `PUT /machines/:id` answers `409 machine_busy`, and `POST /updates/apply` answers `409 machines_busy` while any job is active (the update restarts the server).
- **A node without a token can be saved** (the token is optional in the connection) and a request body that does not read comes back as `{error, detail}` (`bad_request`, `too_big`) like every other refusal.
- **Guessing the setup code is slowed down** like the passwords, and the table of wrong passwords per name no longer grows without limit.
- **The websocket of the events** asks every 30 seconds whether its session is still good and closes when it is not.
- **The fleet tells the line** a G-code job has reached, and the manifest declares the service (port, health path and unit) so that an update checks it came back.
- **The published binaries are built with `--features serial`** and the CI builds and tests that variant too.

## [0.0.7] - Times of the GRBL lines and the homing

- **Waits of a GRBL machine by the kind of line:** `grbl_line_timeout_s` (5 s), `grbl_homing_timeout_s` (120 s) and `grbl_jog_timeout_s` (60 s) in `server.cfg` (each from 1 to 3600), so that a `$H` of a machine that allows the `$` lines has time to finish while an ordinary line still fails quickly. A line that does not end in time holds the machine (a homing cycle is reset, a jog cancelled) and fails the job with the line. Needs the controller crate of EH3D-COMMON with the same change.
- 1 test more (the three settings, their defaults and their range), and the job that carries `$H` and `$J=` runs on the simulator.

## [0.0.6] - Resume a stopped job from its saved request, and a switch for the dollar lines of GRBL

- **Going on from a stopped job without asking for the file again:** the server keeps the request of every job as it came (the file, the tool table, the options, the program text) and gives it back with `GET /api/v1/jobs/:id/request` (operator or administrator; it goes with the job and is no bigger than a request may be). `POST /api/v1/jobs/:id/resume-from` makes a new job, ready and never started, from a cancelled or failed one with its `skip` brought forward to what it had done: the holes done for drilling, the paths finished for routing (the one cut short is cut again) and the `line` for G-code, adding up over several stops. The body may name `skip`, `skip_tools`, `restore_outputs` and `name`; `409 not_stopped` for a job that did not stop. The new job waits for a person to start it, and a G-code one waits for the operator before its first move. Jobs carry `resumed_from`.
- **A switch per machine for the `$` lines of GRBL:** the machine member `allow_dollar` (off by default, changed only by an administrator, kept when an update does not name it) lets the G-code jobs of that machine carry lines such as `$H`, `$X`, `$G` and `$J=...`. `$RST`, the real-time characters and any `$` line with odd signs are refused with `bad_gcode` even then, and a ready job is judged again when it starts, so turning the switch off stops a job made while it was on.
- 5 tests more (the dollar lines and what is refused with them, going on from a drilling, a routing and a G-code job, the roles, the sums over two stops, the switch of a machine).

## [0.0.4] - G-code jobs, pause and resume, GRBL machines and the spindle of the machine

- **Free G-code jobs:** a job request of `"kind": "gcode"` carries the text of a program; the server cleans it into the lines it sends (no comments, no settings or real-time commands of the controller: `bad_gcode`), judges its `S` and `F` against the spindle of the machine like any other job, and runs it line by line on a machine whose connection is `demo` (the simulator) or the new `grbl` (a GRBL controller on a serial port of the server, `port` and `baud`; build with `--features serial`). The view gives the bounds, the length and the time of the moves; the job reports `items_done`, `items_total` and the `line` it has got to.
- **Hold, resume and go on after a stop:** `POST /jobs/:id/pause` and `/resume` hold and release a running G-code job (`confirm` releases it too); a job made with `skip` (the lines already done) gives the codes in force back and waits for the operator before its first move, and `restore_outputs` starts the spindle and the coolant again only when asked. A line the controller refuses, an alarm or a link that fails ends the job as failed, says which line, and stops the controller. A machine of one kind refuses the jobs of the other (`wrong_machine`).
- **A setting for the end of a job:** `gcode_finish_wait_s` in `server.cfg` (900 by default) is how long a G-code job waits for the machine to be still after its last line.
- 20 tests more (the cleaning and reading of a program, the run on the simulator, hold and resume, the line a failed job starts from, the machines that take each kind of job, the spindle switch, and the excesses of the spindle reaching the program that sent the job).

## [0.0.3] - Tools switched off, the spindle of the machine and a switch for its limits

- **Tools switched off and jobs that go on, in the job request:** a drilling or routing job takes `skip_tools` (the tools or pens that are off: their holes or paths are left out and they need not be in the tool table) and `skip` (how many holes, in the order the machine drills them, or paths are already done), and the view tells what was left out (`skipped_tools`, `skipped`); a job with nothing left is refused with `no_work`. A drilling job and a routing job one after the other, each with its tools off, run on the simulator through the real programs. 7 tests.

- **The spindle of the machine, and a safety switch for the limits of the spindle:** a machine says which spindle it carries (`spindle`: `original` or `vfd`) and the server knows the limits of each (the slowest and the fastest turns, the feed along the cut and of the plunge, the power, the thickest bit; the starting values are the ones of the programs and a machine changes only the members it names). `GET` and `PUT /api/v1/machines/:id/spindle` (the change is for an administrator) show and set the spindle, the switch `guard` and the limits, and answer the top speed the node of the machine should be set to (`node_max_rpm`). With a spindle chosen, a job whose turns or feeds go beyond its limits is refused with `422 spindle_limit` (and says which tool and by how much), both when the job is made and when it starts, so a job made for one spindle does not run on the other; the switch `guard` is `reject` by default, and with `warn` the job goes through with the turns cut to the top of the spindle, so the node is never asked for more, and every excess is listed in `spindle_warnings` of the view. A machine with no spindle chosen is judged by nothing, as before, and an update of a machine from a client that does not name the spindle leaves it as it was. 13 tests.

- **Updates from GitHub:** with `updates_dir` the server offers (`GET /api/v1/updates`, `POST /api/v1/updates/check` and `/apply`, administrator only) the check of the latest releases and the update of the server and of Studio; a small helper started by systemd (`deploy/eh3d-update.py`) does the downloading, checks the SHA-256, replaces the installed folder (keeping the old one) and restarts the service. ## [0.0.1] - The server: users, machines, jobs and the run through a node

- **Jobs:** a drilling job (holes and tools, or an Excellon file with its tool table) or a routing job (paths and tools, or an HP-GL file with its tool table), planned with the libraries of EH3D-DRILLPRO and EH3D-ROUTEPRO and the constants and tuning of the machine; refused with a code when a hole or a point is outside the table, a tool is missing or out of range, or the request is too big.
- **Preview:** the work in the order the machine does it, the tools with their count, the bounds, an estimate of the time and the item at which each hole ends.
- **Run:** a job is ready until a person starts it, one job at a time on a machine; it runs on the library of the programs, waits at the dialogs of the operator, can be stopped and is marked failed if the server stopped while it ran.
- **Machines:** an EH3D-NODE-BUNGARD over the network or the simulator, the text of the configuration files and the tuned values; the token of a node is never shown.
- **People and programs:** users with three roles, tokens for programs shown once, Argon2 password hashes, SHA-256 token hashes, a slowdown on wrong passwords and a set-up code on the console for the first administrator.
- **Events:** a websocket with every change of a job.
- **Service:** one binary, a settings file, port 18200 by default, a systemd unit for the CM5.
- 39 tests (unit tests and the interface end to end against the simulator), `cargo clippy -D warnings` and `cargo fmt --check` in CI on Linux and Windows, and a repository check of the manifest, the versions, the changelog and the eight README files.

# Changelog

All notable changes to this project are documented here.

## [Unreleased]

- **The server of every EH3D application, with four common services** (`docs/SERVICES.md`): a store of projects and files, shared catalogs, machine plugins with a generic queue of jobs and a stream of events, and one login. Nothing that existed changes: the routes, the answers and the tests of the first version stay as they were.
- **The project store** (`/api/v1/apps/{app}/projects`, `docs/PROJECT_STORE.md`): the projects and files of each application, a file is never overwritten (every write is a new version with its SHA-256, the last `project_versions_kept` are kept), a write over an existing file needs `If-Match` (`428`/`412`), an editing lock with an expiry, safe file names (nothing that leaves the folder, no Windows device names, no names that differ only in letter case), the bytes checked against their hash at every read, limits per file, per project and per application in `server.cfg`, and import and export of the `.eh3dproj` container with the `eh3d-container` library of EH3D-COMMON.
- **Shared catalogs** (`/api/v1/catalogs`, `docs/CATALOGS.md`): the materials of `eh3d-materials` (built in, read-only) and the tools, machine profiles, footprints, symbols and components (`phoenix-parts/1`) that an administrator uploads as JSON or CSV, read by everybody with search, filters, sorting, pages, `ETag` and `If-None-Match`; an upload that does not fit is refused whole.
- **Machine plugins, a generic queue and events** (`/api/v1/plugins`, `/api/v1/work`, `/api/v1/events/stream`, `/api/v1/notifications`, `docs/MACHINE_PLUGINS.md`): the trait `MachinePlugin` (prepare, start, pause, resume, stop, status, capabilities), the `bungard` plugin over the machines and jobs the server already had, a `demo` plugin without hardware, a queue of jobs with states and a history of every change, a stream of server-sent events with numbers, filters by machine, project, job and application, reconnection with `Last-Event-ID`, a limit of clients and of queue, and notifications for the owner of a job.
- **One login for every application** (`/api/v1/auth`, `docs/AUTH.md`): a login says which application it is for (`app`) and the claims tell it with the role, sessions that a person lists and closes one by one (an administrator anybody's), renewal up to a limit, a limit of open logins per person, a policy for passwords (`password_min_len`, `password_classes`, `password_deny_name`) and for lockout (`auth_max_failures`, `auth_lockout_s`), `GET /auth/policy` with the switches of security for Studio (no secret in it), and audit lines for the logins, the refusals (`denied`, with `audit_denials`) and the closings.
- **New scopes** `catalog:read`, `catalog:write` and `machines:manage` (the last one never held by the tokens of the design programs), and 21 new error codes with stable statuses.
- **Settings:** 26 new keys in `server.cfg`, all with conservative defaults and explained in `server.cfg.example`. Three defaults are stricter than before on purpose: a password may not contain the name of its user, the refusals with `401` and `403` are audited, and the logins of `/auth/login` are limited to twenty per person.
- **The contract and the documents:** the OpenAPI document describes 47 new operations (tags `store`, `catalogs`, `work` and `auth`), `docs/SERVICES.md` explains how an application uses the four services, the architecture and structure pictures and the READMEs in the eight languages are up to date, and the count of tests is 328 (181 in the modules and 147 on the interface end to end).

- **Chained tool changes and places for the tools (`request_version: 2`, `rack`):** a drilling or routing job on a machine with the automatic tool changer may carry a `rack` (`first`, `carry_in`, `carry_out`, `slots`, `carry_slot`, every field optional). The planner then takes each tool from its place, puts the tool in the chuck back in its own place, leaves the last tool in the chuck when the job is followed by another (`carry_out`) and, for the job that comes after, makes one change from the place of the last tool to the place of the first one without asking for the spindle again (`carry_in`). The job and its view answer `rack_applied`; a request without a `rack`, or of the first version, is planned exactly as before. 8 tests in the modules and 6 on the interface (`tests/rack.rs`).
- **What is left out is told, what does not fit is refused:** `view.warnings` lists `rack_needs_v2` (a `rack` in a request of the first version), `rack_no_changer` (the machine changes its tools by hand), `rack_unknown_field` (a field of a later version, ignored) and `request_version_newer`; a place given to two tools, the test pin as a place, a `carry_slot` that does not fit, a place the machine file does not define or reach, or more places than allowed is refused with `422 bad_rack` and a stable sentence.
- **`rack_max_slots` in `server.cfg`** (1 to 14, default 14) is the most places a request may name; the audit line of a job created with a `rack` says `rack=applied` or `rack=left_out`; the permissions are those of any job (operator or administrator, never a viewer).
- **The contract is documented:** `docs/ATC_CHAIN.md`, the schemas `JobRackV2` and `RackSlot`, `rack_applied` in `JobResponse` and in the view, and the code `bad_rack` in the OpenAPI document, the table of the error codes and `docs/API.md`.

## [0.1.2] - OpenAPI contract of the interface, attested release builds and the real test count

- **The contract of the interface is an OpenAPI document:** `docs/openapi.yaml` (OpenAPI 3.1, "EH3D Server API", with the version of the server) describes all 83 operations of the router with their tag, the role and scope each one needs, the schemas of what it takes and gives, examples and the error codes it can answer with (their status comes from `docs/error-codes.json`); `docs/openapi.json` is the same document for the tests and `docs/ROUTES.md` is its table of routes. `tools/make_openapi.py` writes the three files; `tests/openapi.rs` (6 tests) and `tools/check_openapi.py`, which the CI runs, check that every route of the router is in the document and the other way round, that every operation has a summary, a tag, a role and responses, that the error codes exist in the catalog with a status the operation answers, and that the YAML and the table say the same as the JSON. `docs/API.md` and `tests/routes_doc.rs` name it as the contract of the routes. 7 tests.
- **The count of tests is the real one:** the READMEs said 160 tests; the suite has 231 (135 in the modules and 96 on the interface end to end).
- **Brand:** Add the application icon and the logos of the program.
- **Release builds are checked and attested:** `release-binaries.yml` takes the owner's go-ahead only (a manual start from main, the commit must be part of main), builds the same packages as before, writes `SHA256SUMS` and a build manifest, attests their provenance, verifies the artifact as a stranger would, prepares a draft release of unsigned files only after the owner approves it (a dry run is the default) and opens an issue `build-failed` when anything does not finish.
- **Shared checks updated:** the validator also compares the badge and the Version row of the README with the manifest, fails when one of its checks cannot run, and the CHANGELOG step of the workflow reads the base branch from the environment.

- **Artifacts, blobs and uploads:** the files of the design programs and of the tasks are kept as artifacts (`artifact_id`) apart from the bytes (`blob_sha256`, stored once). Upload in one request or in parts, download streamed, retention (`keep_while_referenced`, `pinned`, `keep_until`), a check of every blob against its hash, and limits in `server.cfg` (`artifact_store_gb`, `max_upload_mb`, `upload_ttl_s`, `uploads_per_user`, `artifact_unreferenced_days`).
- **Projects with an owner and explicit sharing:** projects with revisions, shared one person or token at a time with `read` or `write`; what is not visible does not exist for the caller. `shares_enabled = false` switches sharing off; nothing is shared by default.
- **Events filtered by who may see them:** the websocket sends the events of a project and of a task only to the owner, the people it is shared with and the administrators.
- **Tokens with a template and scopes:** `phoenix`, `cam`, `client` and `custom` templates, scopes that narrow a role (never widen it), `403 forbidden_scope`, and `POST /tokens/:id/rotate`. The templates of the design programs can never hold the scopes of the machines.
- **The fleet tells the tool at work:** the `job` of a machine in `GET /fleet` has `tool`, the drill or pen being used now (or the one the operator is asked to put in); `null` for a G-code job.
- **The update helper's signature check is described in the README** (`/etc/eh3d-update.signers`), and the issue template for hardware validation exists.
- **The workflows are hardened:** every action is pinned by its commit with its version in a comment, the checkouts keep no credentials, and the release workflow runs only for the owner on main, with no cache and the values of the matrix passed by environment.

## [0.1.1] - Records, audit, error catalog and honest logins
- **A log of the jobs on the disk:** `eh3d-jobs.log` in the data folder gets a line when a job starts (job, machine and how it is reached, who asked for it and who started it, a short hash and the size of the request, the holes or paths, the items, the estimate) and a line when it ends (result, message, how far it got, who stopped it, the real duration against the estimate), set aside at `log_max_kb`; `job_log` turns it off. 2 tests.
- **One catalog of the error codes:** `src/errors.rs` lists every code the API answers with, its usual status and what it means; a test reads the source and fails when a code is used that the catalog lacks (or the catalog keeps one that is gone), writes `docs/error-codes.json` for the clients and checks that `docs/API.md` has a row for each. The Studio checks its texts against that file (`tools/sync_api_examples.py` copies it). 3 tests.
- **An audit of who did what:** every login (also the failed ones, with the code and the address), set-up, logout, password change, job (create, start, confirm, pause, resume, cancel, delete, end), stop of a machine, change of machines, spindles, users and tokens, and update is a line `event=... who=... role=...` on the console and, with `audit_file`, in `audit.jsonl`; a job carries `started_by` and `stopped_by`. 1 test.
- **The websocket of the events pings and tells a client to ask again:** it sends a ping every `events_ping_s` seconds and closes a connection that has said nothing, a pong included, for `events_idle_s`; a client that fell behind gets `{"type":"resync","missed":N}` instead of losing events without knowing. Tested on a real socket. 3 tests.
- **Tokens of programs with a last use and an optional expiry:** `POST /tokens` takes `days` (1 to 3650, else `bad_days`) and `token_default_days` of `server.cfg` sets the default (0: no expiry); the list says `expires` and `last_used` (exact in memory, written to the disk at most once an hour). 5 tests.
- **Logins that survive a restart:** `sessions.json` keeps only the SHA-256 of each login token, so an update or a power cut does not log anybody out; logins that ended, of users deleted or disabled, or ended with logout are not taken up again. It is off by default (`persist_sessions = true` turns it on); with it off a restart logs everybody out and the file is removed. 4 tests.
- **A panic stops the machines and the server restarts (`exit_on_panic`, on by default):** the hook stops the running jobs and exits so that systemd starts the server again; off, the panic is only written and the server goes on with its locks recovered. 2 tests.
- **The proxy header only from the local proxy (`trust_forwarded_for`, off by default):** with it on, and only on a connection from 127.0.0.1, the last address in `X-Forwarded-For` is the client for the limit of wrong passwords and for the audit; any other connection is judged by its socket whatever the header says. 1 test.
- **The progress of a routing job counts paths:** the view of a route takes the item that ends each path from the planner (`hole_ends`), so `holes_done` follows the paths done. 1 test.
- **The health check tells the new switches** (`trust_forwarded_for`, `exit_on_panic`, `persist_sessions`) to whoever is logged in.
- **The maturity is functional:** the manifest, the badge and the table of the eight README files say it, since it is used and tried with real files; the evidence stays as host tests.

- **The warnings and the course of a plan come from EH3D-COMMON (`eh3d-summary`):** the view of a plan says the same as before; the types are taken from the shared crate instead of through the drilling program.

## [0.1.0] - Operation, resuming and a dry run before moving a machine

- **An orderly stop on SIGTERM too:** `systemctl stop` and containers send SIGTERM, and the server now stops the machines that are running and exits with a success status on it, as it does on Ctrl-C; the unit no longer needs `KillSignal=SIGINT`. `--version` prints the version. A test starts the real binary and sends it SIGTERM (systems with signals).
- **A hardened unit:** `UMask=0077`, the group `dialout` for the serial ports, no home folders, no kernel or control-group changes, no new privileges, only IP and unix sockets; `tests/test_deploy_files.py` keeps the unit as the guide describes it.
- **A health check that tells something:** `GET /api/v1/health` adds `api_revision` and `status` (`ok`, or `degraded` when the data folder takes no file or a lock was taken over after a panic); who is logged in also gets `uptime_s`, `storage`, `recovered_locks` and `features`. The anonymous answer stays small. Examples `health.json` and `health_detail.json`. 2 tests.
- **A panic does not leave the server half dead:** the locks of the state are taken over when a thread panicked while holding one (they were poisoned and made every later request panic), the count is told by the health check, and the stop of a serial link works the same way. 2 tests.
- **A smoke test of the binary in the release workflow:** `tools/smoke_binary.py` starts the built server on a free port, checks its health check against `--version` and stops it.
- **A nightly backup of the data folder:** `deploy/eh3d-backup.py` with a systemd timer writes a `.tar.gz` (owner-only, read back to check it, files being written left out) and keeps the newest ones (`backup.cfg`: `source`, `dest`, `keep`); `docs/DEPLOY.md` explains the restore. 7 tests.
- **A guide to HTTPS that can be copied:** `deploy/Caddyfile.example` (Caddy with its own certificate authority, the server listening only on 127.0.0.1) and the steps to trust the certificate; it says to turn `login_ip_limit` off behind the proxy.
- **The tests of the helpers of the deployment run in the CI.**

- **Examples of the answers, made by the tests:** `tests/examples/*.json` (session, health, preview, error, job, jobs, fleet, spindle and updates) are made from the real router, and the tests fail when a file is not what the server answers; `tools/sync_api_examples.py` copies them to the clients, which read them in their own tests.
- **The last update can be undone:** `POST /api/v1/updates/undo` asks the helper to put back the version that the last update of a service left behind (the version installed takes its place, so doing it twice goes forward again); each component of `GET /api/v1/updates` says `can_undo` and, when the helper knows it, the `previous` version. The helper writes `previous.json`, marks what it installs with its version and restarts the server when it is the server that goes back; it refuses while a job is active. 6 tests.
- **The history of the updates can be emptied:** `POST /api/v1/updates/clear-history` asks the helper to empty `history.json`; that request is not kept in the history it empties.
- **A dry run of the exact plan before any job exists:** the steps of a drilling or routing job are followed on paper, the way the control unit reads them, and the view of the job gets `dry_run` (how far each axis goes from its switches, where the plan ends, the steps and the seconds, and whether it stays inside the course of the machine file). A plan that takes an axis past its course is refused with `422 outside_course`, saying which axis and by how much; the tuning of the machine decides with `dry_run = reject` (the default) or `warn` (the job goes through and the excess is listed), and `dry_run_margin_mm` (0.5) is the play that is forgiven.
- **Sanity checks of the work in the view:** `warnings` lists what looks wrong in the file (`tiny`: the whole work is smaller than `sanity_tiny_mm` in both directions, a wrong unit; `too_big`: bigger than the table; `far`: starts further than `sanity_far_mm` from the corner; `scale`: the machine file stretches the work; `out_of_course` with `warn`). They only warn; the thresholds are keys of the machine's tuning. 4 tests.

## [0.0.9] - The steps, the notes and the history of an update reach the Studio

- **The steps of an update with a percent:** the helper writes the steps of the job (download, check, install and restart of each service) with their state and the percent of the whole, and the server gives them in `GET /api/v1/updates` (`steps`, `percent`); the step that was running when a job failed is marked as failed.
- **The notes of the release:** the check keeps the text of the latest release of each service and the server gives it as `notes` of the component, so the Studio can show what changes before updating.
- **A history of the jobs:** the last fifteen checks and updates (`history`), kept by the helper in `history.json`.
- **Compatible both ways:** a helper that is older leaves the new fields empty and the Studio shows the page as before; tests for the helper (steps, failed step, notes and history) and for the answer of the server.

## [0.0.8] - A stop that reaches the machine at once, files that survive a power cut and a token out of the address

- **Each dependency on a sibling repository by path says the version it needs** (`version = ">=0.0.1", path = "../EH3D-..."`), so Cargo stops at once when the sibling next to this one is older than the program expects.
- **Files that survive a power cut:** the JSON files of the server (users, tokens, machines, the list of the jobs and the request of each job) are flushed to the disk before they replace the old file and the folder is flushed after it; the file that is replaced (and the list of the jobs) is kept once as `<name>.bak`. A damaged file is still an error, but when the copy is good the error names it and says how to recover; it is never loaded by itself.
- **The slowest turn of the original spindle is 5000 rpm** (the figure of the maker's page; it started from 3000), and the documentation of the starting limits says 5000 to 63000 turns.
- **The stop button reaches the machine at once:** `POST /machines/:id/stop` ends the job that is active on a machine whoever asks and whatever the job is; on a GRBL machine the feed hold and the soft reset are written to the port from another thread (the port is shared, the waits are made in short turns), so a homing cycle or a long move no longer has to end before the stop is heard. A line that was waiting when the stop came does not make the job fail: it is cancelled. `POST /jobs/:id/cancel` takes the same way.
- **The token stays out of the address:** `POST /tickets` gives a ticket good for one use within 30 seconds, for the camera and the websocket; `?token=` in the address is refused unless `url_token = true` is set.
- **`local_until_setup` in `server.cfg`** (off by default: the server answers whoever reaches it, as it always did): while there is no user yet, only connections from 127.0.0.1 are answered (`403 local_only` for the rest), so nobody else on the network can make the first administrator; once there is a user it makes no difference.
- **The update helper can require a signature:** when the machine has a file of allowed signers (`/etc/eh3d-update.signers` or `--signers`), only a release that publishes `<file>.sig` (an OpenSSH signature made with `ssh-keygen -Y sign -n eh3d-release`) that verifies against one of those keys is installed; without the file it works as before and says in its log that the hash proves the file arrived whole, not who made it. No key is made by the project: the owner makes one and publishes the signatures.
- **The request of a job is a file of its own** (`requests/<id>.json`) and `jobs.json` no longer carries it; the files are written by a thread of their own, so the lock of the jobs is never held for the disk. A `jobs.json` of an older version is read and its requests are moved to files.

- The release workflow runs `cargo test --all-targets` before it builds the packages.

- **A resumed G-code job goes back a margin of lines** (`resume_margin_lines` in `server.cfg`, 16 by default, 0 to 1000): the controller takes lines ahead of the movement, so the last ones it took were not all done. The codes in force are still given back before the first move.
- **Wrong passwords are also counted by address** (`login_ip_limit`, 10 by default, 0 turns it off): the address is the one of the connection, never a header, and a person who tries many names from one address is slowed down without blocking the names of the others.

- **The secrets of the tuning text stay on the server:** `GET /machines` and `GET /machines/:id` show `head_token`, `node_token` and any other `*_token`, `*password` or `*_secret` key with an empty value, and a `PUT` that sends them empty keeps the stored ones.
- **A started job cannot be undone by a late start:** a job cancelled or removed while it was being planned is not started any more, and `DELETE /jobs/:id` checks and removes under one lock.
- **A machine with a job running is not edited:** `PUT /machines/:id` answers `409 machine_busy`, and `POST /updates/apply` answers `409 machines_busy` while any job is active (the update restarts the server).
- **A node without a token can be saved** (the token is optional in the connection) and a request body that does not read comes back as `{error, detail}` (`bad_request`, `too_big`) like every other refusal.
- **Guessing the setup code is slowed down** like the passwords, and the table of wrong passwords per name no longer grows without limit.
- **The websocket of the events** asks every 30 seconds whether its session is still good and closes when it is not.
- **The fleet tells the line** a G-code job has reached, and the manifest declares the service (port, health path and unit) so that an update checks it came back.
- **The published binaries are built with `--features serial`** and the CI builds and tests that variant too.

## [0.0.7] - Times of the GRBL lines and the homing

- **Waits of a GRBL machine by the kind of line:** `grbl_line_timeout_s` (5 s), `grbl_homing_timeout_s` (120 s) and `grbl_jog_timeout_s` (60 s) in `server.cfg` (each from 1 to 3600), so that a `$H` of a machine that allows the `$` lines has time to finish while an ordinary line still fails quickly. A line that does not end in time holds the machine (a homing cycle is reset, a jog cancelled) and fails the job with the line. Needs the controller crate of EH3D-COMMON with the same change.
- 1 test more (the three settings, their defaults and their range), and the job that carries `$H` and `$J=` runs on the simulator.

## [0.0.6] - Resume a stopped job from its saved request, and a switch for the dollar lines of GRBL

- **Going on from a stopped job without asking for the file again:** the server keeps the request of every job as it came (the file, the tool table, the options, the program text) and gives it back with `GET /api/v1/jobs/:id/request` (operator or administrator; it goes with the job and is no bigger than a request may be). `POST /api/v1/jobs/:id/resume-from` makes a new job, ready and never started, from a cancelled or failed one with its `skip` brought forward to what it had done: the holes done for drilling, the paths finished for routing (the one cut short is cut again) and the `line` for G-code, adding up over several stops. The body may name `skip`, `skip_tools`, `restore_outputs` and `name`; `409 not_stopped` for a job that did not stop. The new job waits for a person to start it, and a G-code one waits for the operator before its first move. Jobs carry `resumed_from`.
- **A switch per machine for the `$` lines of GRBL:** the machine member `allow_dollar` (off by default, changed only by an administrator, kept when an update does not name it) lets the G-code jobs of that machine carry lines such as `$H`, `$X`, `$G` and `$J=...`. `$RST`, the real-time characters and any `$` line with odd signs are refused with `bad_gcode` even then, and a ready job is judged again when it starts, so turning the switch off stops a job made while it was on.
- 5 tests more (the dollar lines and what is refused with them, going on from a drilling, a routing and a G-code job, the roles, the sums over two stops, the switch of a machine).

## [0.0.5] - The original spindle starts from the speed of the maker

- **The original spindle starts from the speed of the maker:** 3000 to 63000 rpm and 150 W (the KaVo spindle of the CCD, as the manual and the catalogue of Bungard say) instead of 10000 to 60000 rpm and 200 W; the settings of a machine still replace them.

## [0.0.4] - G-code jobs, pause and resume, GRBL machines and the spindle of the machine

- **Free G-code jobs:** a job request of `"kind": "gcode"` carries the text of a program; the server cleans it into the lines it sends (no comments, no settings or real-time commands of the controller: `bad_gcode`), judges its `S` and `F` against the spindle of the machine like any other job, and runs it line by line on a machine whose connection is `demo` (the simulator) or the new `grbl` (a GRBL controller on a serial port of the server, `port` and `baud`; build with `--features serial`). The view gives the bounds, the length and the time of the moves; the job reports `items_done`, `items_total` and the `line` it has got to.
- **Hold, resume and go on after a stop:** `POST /jobs/:id/pause` and `/resume` hold and release a running G-code job (`confirm` releases it too); a job made with `skip` (the lines already done) gives the codes in force back and waits for the operator before its first move, and `restore_outputs` starts the spindle and the coolant again only when asked. A line the controller refuses, an alarm or a link that fails ends the job as failed, says which line, and stops the controller. A machine of one kind refuses the jobs of the other (`wrong_machine`).
- **A setting for the end of a job:** `gcode_finish_wait_s` in `server.cfg` (900 by default) is how long a G-code job waits for the machine to be still after its last line.
- 20 tests more (the cleaning and reading of a program, the run on the simulator, hold and resume, the line a failed job starts from, the machines that take each kind of job, the spindle switch, and the excesses of the spindle reaching the program that sent the job).

## [0.0.3] - Tools switched off, the spindle of the machine and a switch for its limits

- **Tools switched off and jobs that go on, in the job request:** a drilling or routing job takes `skip_tools` (the tools or pens that are off: their holes or paths are left out and they need not be in the tool table) and `skip` (how many holes, in the order the machine drills them, or paths are already done), and the view tells what was left out (`skipped_tools`, `skipped`); a job with nothing left is refused with `no_work`. A drilling job and a routing job one after the other, each with its tools off, run on the simulator through the real programs. 7 tests.

- **The spindle of the machine, and a safety switch for the limits of the spindle:** a machine says which spindle it carries (`spindle`: `original` or `vfd`) and the server knows the limits of each (the slowest and the fastest turns, the feed along the cut and of the plunge, the power, the thickest bit; the starting values are the ones of the programs and a machine changes only the members it names). `GET` and `PUT /api/v1/machines/:id/spindle` (the change is for an administrator) show and set the spindle, the switch `guard` and the limits, and answer the top speed the node of the machine should be set to (`node_max_rpm`). With a spindle chosen, a job whose turns or feeds go beyond its limits is refused with `422 spindle_limit` (and says which tool and by how much), both when the job is made and when it starts, so a job made for one spindle does not run on the other; the switch `guard` is `reject` by default, and with `warn` the job goes through with the turns cut to the top of the spindle, so the node is never asked for more, and every excess is listed in `spindle_warnings` of the view. A machine with no spindle chosen is judged by nothing, as before, and an update of a machine from a client that does not name the spindle leaves it as it was. 13 tests.

## [0.0.2] - The quality check through the camera of the drill head

- **The quality check through the camera of the head:** `GET` and `POST /api/v1/machines/:id/head/light` (the ring of LEDs), `GET .../head/snapshot` (one picture), `POST .../head/inspect` (the light, the picture, the analysis with the profile of the machine and the colour of the ring that says how it went), `GET .../head/inspect` (the last check), `GET` and `PUT .../head/inspect/profile` (tolerances and presets) and `POST .../head/inspect/calibrate` (the scale from the hole that was measured). The profile of each machine is kept by the server; a query for the ring that has signs the node does not use is refused (`422 bad_light`).

- **The node of the drill head through the server:** `GET /api/v1/machines/:id/head/status`, `POST .../head/measure` and `GET .../head/stream` hand on the status, a measure of the table and the camera (MJPEG) of the node that the machine's configuration names (`head_address`, `head_token`), with the roles viewer, operator and viewer; the token of the node never leaves the server. Tested against a stand-in node.

## [0.0.1] - First release: the server of the machines, the fleet, the pages of Studio and the updates from GitHub

- **Updates from GitHub:** with `updates_dir` the server offers (`GET /api/v1/updates`, `POST /api/v1/updates/check` and `/apply`, administrator only) the check of the latest releases and the update of the server and of Studio; a small helper started by systemd (`deploy/eh3d-update.py`) does the downloading, checks the SHA-256, replaces the installed folder (keeping the old one) and restarts the service. A workflow builds the packages of the server for Linux (x86_64 and aarch64), Windows and macOS.
- **The pages of Studio from the server:** the setting `studio_dir` names a folder with the pages of EH3D-STUDIO and the server serves it at `/` on its own address (a page that is not a file is the start page, so a reload works); without it the server answers only the API.
- **Several machines and stations at once:** a machine has a `station` (the bench, the room or the workshop it belongs to), and `GET /api/v1/fleet` answers for every machine in one request, grouped by station, with what each one is doing (free, busy, waiting for the operator), its job with the progress and the number of jobs ready; the machines run at the same time, one job on each (a test runs jobs on two machines of two stations together).
- **A lighter debug build:** the `dev` profile keeps the file and line of a panic (`debug = "line-tables-only"`) but not the full debug symbols, so the `target` folder of a test run is about a tenth of its size.
- **README in the universal layout, in eight languages:** the README has the same sections in the same order as the other repositories of the family (status, overview, architecture, features, security, interfaces, configuration, quick start, testing, structure, roadmap and known limits), with figures taken from the code and from the tests that were run. The Architecture and Repository Structure pictures are drawn from `docs/architecture.json` and `docs/structure.json` by `tools/make_architecture.py` and `tools/make_structure.py`, and the CI checks that they match.
- **The build, build-test and test scripts show a live panel:** a banner with the name and version, one line per step with its time, the number of tests that passed and a summary at the end, with the whole output kept in a log file. `test.sh` and `test.bat` run only the tests and never change the version; without `tools/pretty_run.py` the scripts behave as they always did.
- **The layout of the README is checked in the CI:** the validator runs `tools/universal_readme_check.py` and lists, as a warning, what differs from the universal layout of the README.

## [0.0.1] - The server: users, machines, jobs and the run through a node

- **Jobs:** a drilling job (holes and tools, or an Excellon file with its tool table) or a routing job (paths and tools, or an HP-GL file with its tool table), planned with the libraries of EH3D-DRILLPRO and EH3D-ROUTEPRO and the constants and tuning of the machine; refused with a code when a hole or a point is outside the table, a tool is missing or out of range, or the request is too big.
- **Preview:** the work in the order the machine does it, the tools with their count, the bounds, an estimate of the time and the item at which each hole ends.
- **Run:** a job is ready until a person starts it, one job at a time on a machine; it runs on the library of the programs, waits at the dialogs of the operator, can be stopped and is marked failed if the server stopped while it ran.
- **Machines:** an EH3D-NODE-BUNGARD over the network or the simulator, the text of the configuration files and the tuned values; the token of a node is never shown.
- **People and programs:** users with three roles, tokens for programs shown once, Argon2 password hashes, SHA-256 token hashes, a slowdown on wrong passwords and a set-up code on the console for the first administrator.
- **Events:** a websocket with every change of a job.
- **Service:** one binary, a settings file, port 18200 by default, a systemd unit for the CM5.
- 39 tests (unit tests and the interface end to end against the simulator), `cargo clippy -D warnings` and `cargo fmt --check` in CI on Linux and Windows, and a repository check of the manifest, the versions, the changelog and the eight README files.
